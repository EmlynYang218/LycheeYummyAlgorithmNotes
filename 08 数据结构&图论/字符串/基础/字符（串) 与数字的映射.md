# 三种映射构建方法整理（以三道题为例）

这三道题恰好覆盖了"字符/字符串 → 值"映射的三种典型做法，按**查找结构**和**适用规模**可以整理成一个知识点。

---

## 一、总览对照表

| 题目          | 映射键 → 值             | 方法                        | 查找复杂度            | 为什么选它            |
| ----------- | ------------------- | ------------------------- | ---------------- | ---------------- |
| DNA 相似度     | 字符 `A/G/C/T` → 0..3 | **定长数组直接下标** `idx[256]`   | O(1) 一次内存访问      | 键是单字节字符，值域小且固定   |
| 478-3279 电话 | 字符 `0-9/A-Z` → 数字   | **定长数组直接下标** `mp[256]`    | O(1) 一次内存访问      | 同上，键是单字节，需逐字符高频查 |
| 行星旅行        | 字符串 `"Mars"` → 行星编号 | **定长 `struct` 数组 + 线性查找** | O(k)，k=元素数（此处 8） | 键是多字符串，元素极少（8 个） |

**核心规律**：

- **键是单字节字符** → `int table[256]` 直接下标，O(1)，最优先。
- **键是字符串/复合类型、元素很少** → 定长数组 + 线性查找，O(k) 但 k 小，cache 友好，胜过哈希。
- **元素很多、键复杂** → 才考虑 `unordered_map` / `map`（本题三道都没到这一步）。

---

## 二、方法 1：定长数组直接下标（字符 → 值）

**适用**：键是单字节（`char`/`unsigned char`），值域可枚举，需高频查询。

**模板**：

```cpp
static int table[256];          // 全局，零初始化

// 初始化（main 开头一次）
for(int c = '0'; c <= '9'; c++) table[c] = c - '0';
table['A'] = table['B'] = table['C'] = 2;
// ...

// 查询（热点内层）
int v = table[(unsigned char)ch];   // unsigned char 防负下标
```

**两个 DNA/电话题的关键细节**：

1. **`unsigned char` 强转**：`char` 可能是 `signed`，若字符值 >127 会变负，索引越界。碱基/字母都是 ASCII 正数，但强转是保险习惯。
2. **"无映射"用哨兵值，别用 0**：电话题踩过的坑——数字 `'0'` 合法映射到 `0`，若用 `0` 表示"无映射"就会误跳过合法字符。**用 `-1`（或先 `memset` 全 `-1`）表示无映射**，判断 `v < 0`。

**优点**：O(1)、零分配、连续内存、编译器可优化；**缺点**：值域必须能用 256（或更大定长）覆盖。

## 三、方法 2：定长数组 + 线性查找（字符串 → 值）

**适用**：键是字符串（或结构），**元素数量少**（几十以内），查询频率中等。

**模板**：

```cpp
struct Item { const char* name; double a, b; };
static const Item T[8] = {
    {"Mercury", 36, 0.27},
    // ...
};

int find(const string& s){
    for(int i = 0; i < 8; i++)
        if(s == T[i].name) return i;
    return -1;
}
```

**为什么元素少时线性查找胜过哈希**：

- 8 次字符串比较的常数开销，远小于 `unordered_map` 的哈希计算 + 桶定位 + 可能冲突链。
- 数组连续存储，8 个元素全在一个 cache line 附近，**线性扫 cache 全命中**；哈希表桶分散，反而 miss。
- 代码简单，无动态分配。

**经验阈值**：元素 **≤ 几十**（如 8、16、50）时，线性查找通常不输甚至胜过哈希；上百以上才考虑 `unordered_map`。

---

## 四、方法 3：哈希表（本题没用到，但要知道边界）

**适用**：键复杂（长字符串、复合键）、元素成百上千、查询极频繁。

```cpp
unordered_map<string,int> um;
um["Mars"] = 3;
int v = um.at("Mars");   // 注意：at 在热点里慢，见 DNA 题 TLE 教训
```

**本题三道为什么不用**：

- DNA/电话：键是单字节，`table[256]` 完胜哈希（DNA 题 TLE 正是 `um.at` 在 `O(as*bs)` 热点里反复哈希导致的）。
- 行星：只有 8 个键，线性查找足够，哈希的常数开销反而更大。

**教训**：**哈希不是万能快**。键简单、元素少时，定长数组/线性查找几乎总是更优。

## 五、决策流程（拿到"映射"需求怎么选）

```
键是什么类型？
├─ 单字节字符（char）
│    └─ 用 int table[256] 直接下标  ← DNA、电话
│         · 无映射用 -1 哨兵，别用 0
│         · 查表时 (unsigned char) 强转
│
└─ 字符串 / 复合类型
     ├─ 元素数量少（≤ 几十）
     │    └─ 定长数组 + 线性查找  ← 行星
     │
     └─ 元素多（上百+）或键很长
          └─ unordered_map / map
               · 热点内层避免 .at()，可先 find 或缓存
```

## 六、三道题的映射代码并排

**DNA（字符→0..3）**：

```cpp
static int idx[256];
idx['A']=0; idx['G']=1; idx['C']=2; idx['T']=3;
// 热点：idx[(unsigned char)a[i-1]]
```

**电话（字符→数字，含无映射）**：

```cpp
static int mp[256];
memset(mp, -1, sizeof(mp));              // 无映射 = -1
for(int c='0'; c<='9'; c++) mp[c]=c-'0'; // '0'→0 合法
mp['A']=mp['B']=mp['C']=2;
// ...
// 热点：int v = mp[(unsigned char)ch]; if(v<0) continue;
```

**行星（字符串→编号）**：

```cpp
static const Planet P[8] = { {"Mercury",36,0.27}, ... };
int findPlanet(const string& s){
    for(int i=0;i<8;i++) if(s==P[i].name) return i;
    return -1;
}
```

## 七、三个易错点（都在这三道题里出现过）

1. **映射表写错键**：DNA 题把 `A/G/C/T` 写成 `A/B/C/D`，`G`/`T` 查不到抛 `out_of_range`。**映射表必须和题目给的键集合严格一致**。
2. **无映射哨兵与合法值冲突**：电话题用 `0` 当"无映射"，把合法的数字 `0` 跳过，WA。**用 `-1` 当哨兵**。
3. **`char` 负下标**：`table[ch]` 若 `ch` 为负则越界，**统一 `(unsigned char)ch` 强转**。

---

## 八、一句话总结

> 映射构建按"键类型 + 元素规模"选结构：**单字节字符 → `int table[256]` 直接下标（O(1)，无映射用 `-1` 哨兵、`unsigned char` 强转）；字符串且元素少 → 定长数组 + 线性查找（8 个元素比哈希快）；元素多/键长才上 `unordered_map`**。三道题正好对应前两种：DNA/电话是字符直接下标，行星是字符串线性查找；共同教训是"映射表键集合要写对、哨兵别和合法值撞、`char` 防负下标"。
